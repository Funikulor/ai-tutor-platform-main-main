### Слайд 5. Результаты: информационное моделирование (модели данных)

**Заголовок:** Информационная модель и хранилище данных

**Текст на слайде:**
- Транзакционные сущности: пользователи, тесты, ДЗ, попытки, чаты
- Когнитивный профиль: `topic_mastery`, `task_history`, `error_frequency`, `accuracy_rate`
- Хранение: PostgreSQL (Railway), профиль/аналитика — JSON в `payload`

**Егор — речь:**
Мы разделили данные на транзакционные и персонализационные. Профиль большой и меняется по мере развития модели, поэтому хранится как JSON в `payload` — это упрощает эволюцию структуры данных.

**Вова — речь:**
Для интерфейса важно, что прогресс и слабые темы — это данные из БД, и UI лишь визуализирует их в дашбордах ученика и учителя.

**⟦Схема⟧:** ⟦ER/инфологическая модель (фрагмент)⟧  
**⟦Код⟧:** ⟦Структура `CognitiveProfile` (краткий фрагмент)⟧  
**⟦Скрин БД⟧:** ⟦Фрагмент `payload`: `task_history` (одна попытка) + `error_history` / `error_frequency`⟧

**Заметка: одна запись `task_history` (история попытки)**

**Текст на слайде (таблица по скрину):**

| Ключ | Смысл | Пример на скрине |
|------|--------|------------------|
| `task_id` | Уникальный ID задания в сессии | `170693` |
| `question` | Условие задачи (как видел ученик) | Уравнение \|2x − 5\| = 9, сумма корней |
| `user_answer` | Ответ ученика | `"4"` |
| `correct_answer` | Эталон для проверки | `"5"` |
| `is_correct` | Результат проверки | `false` → ошибка |
| `time_spent_seconds` | Время на задачу (сек) | `75` |
| `topic` | Тема для `topic_mastery` и адаптации | «общая математика» |
| `timestamp` | Когда отправлен ответ (ISO) | `2026-05-26T20:10:47…` |

*В полной модели также есть `attempts_count`, `error_analysis` — на скрине могут не попадать в кадр.*

**Связь с персонализацией (1 строка на слайде):**  
неверная попытка → −3% к `topic_mastery` по теме → учёт в `accuracy_rate` → при ошибке плюс запись в `error_history` / `error_frequency`.

**Егор — речь (25–30 с):**  
`task_history` — журнал каждой отправки ответа. Мы сохраняем не только «верно/неверно», а условие, ответы, тему и время — чтобы пересчитывать точность, освоение тем и аналитику. На примере: ученик ответил 4 вместо 5 по модулю — попытка помечена `is_correct: false`, тема «общая математика» участвует в выборе следующих заданий.

**Вова — речь (10–15 с):**  
После отправки UI получает результат с сервера; в БД остаётся та же структура — прогресс при следующем входе не «с нуля», а из сохранённого профиля.

---

**Заметка: учёт ошибок в профиле (для слайда / ответов комиссии)**

**Текст на слайде (кратко, 2 колонки или таблица):**

| Блок | Ключ | Смысл |
|------|------|--------|
| Попытка (`task_history`) | `user_answer` / `correct_answer` / `is_correct` | Что ответил ученик, эталон, верно ли |
| Попытка | `attempts_count` | Номер попытки на одно задание (в прототипе обычно `1`) |
| Попытка | `error_analysis` | Разбор одной ошибки в записи попытки (часто `null`; агрегаты — ниже) |
| Журнал (`error_history[]`) | `error_type` | Класс ошибки: `carelessness`, `calculation_error`, `missing_formula`, `concept_confusion`, `logic_gap` |
| Журнал | `justification` | Почему отнесли к этому типу (кратко, по правилам `ErrorAnalyzerAgent`) |
| Журнал | `suggested_remediation` | Что повторить / на что обратить внимание |
| Сводка | `error_frequency` | Сколько раз встречался каждый тип ошибки за всё время |

**Типы ошибок (одной строкой на слайде):**
- `carelessness` — невнимательность, описка  
- `calculation_error` — арифметика  
- `missing_formula` — не применена формула/правило  
- `concept_confusion` — неверное понимание темы  
- `logic_gap` — ошибка в логике решения  

**Егор — речь (30–40 с):**
После неверного ответа `ErrorAnalyzerAgent` сравнивает ответ с эталоном и присваивает тип ошибки. В профиль пишется запись в `error_history` — что за ошибка, обоснование и рекомендация. Параллельно обновляется `error_frequency`: счётчики по типам. Это не просто «неверно», а диагностика для адаптивных заданий и аналитики учителя. Попытки лежат в `task_history`; детальный разбор на уровне профиля — в `error_history` и сводке `error_frequency` в JSON `payload` таблицы `cognitive_profiles` в PostgreSQL на Railway.

**Вова — речь (15–20 с):**
В интерфейсе ученик видит результат и прогресс; учитель — сводку по слабым темам и типичным ошибкам. Типы ошибок с сервера позволяют показывать не только процент верных ответов, но и *характер* проблемы — например, частые описки vs пробел в формуле.

**Если спросят про `error_analysis: null` в `task_history`:**
В модели поле есть, но в текущем потоке orchestrator записывает разбор в `error_history` / `error_frequency`, а не всегда вложением в каждую попытку — поэтому в БД в строке попытки может быть `null`, а тип ошибки — в агрегатах профиля.

Затем профиль становится основанием для выбора слабой темы и подбора материала или подсказки. Таким образом адаптация происходит на каждом шаге обучения, а не один раз в начале курса.

**Визуальные подсказки:**
- Кольцевая диаграмма (cycle diagram)
- Выделить этап “тип ошибки → профиль → рекомендации”

**Технические якоря:**
- Оркестратор координирует агенты
- Ошибки представлены типами, профиль содержит `error_frequency`

### Слайд 6. Архитектура: модули, интеграции и Railway

**Заголовок:** Архитектура системы и облачная инфраструктура

**Текст для тела слайда:**
**Компоненты:**
- **Frontend:** React (кабинеты, задания, библиотека, чат)  
- **Backend:** FastAPI (REST API, безопасность, оркестрация агентов)  
- **LLM‑контур:** AssistantService (запросы к внешней модели для текста и подсказок)  
- **Агенты:**
  - ProfilerAgent — обновление когнитивного профиля
  - ErrorAnalyzerAgent — классификация ошибок
  - MentorAgent — педагогическое сообщение поддержки
  - TaskGeneratorAgent — генерация адаптивных заданий
- **Хранилище:** PostgreSQL на Railway
  - Профили персонализации и аналитика хранятся в JSON‑полях `payload`

**Инфраструктура Railway (важное для защиты):**
- Развёрнуты **frontend + backend + PostgreSQL**
- Платформа доступна по публичной ссылке из интернета
- Фронтенд при сборке использует `VITE_API_URL` для обращения к бэкенду
- Бэкенд использует `DATABASE_URL` для работы с управляемой PostgreSQL на Railway
- CORS настроен на уровне backend так, чтобы браузер мог обращаться к API

**Спикер-скрипт:**
Мы проектировали архитектуру так, чтобы прототип можно было не только запустить локально, но и вывести в эксплуатационную среду. Поэтому ключевые компоненты — frontend, backend и база — размещены на Railway. Это означает, что учётные записи, попытки и профили сохраняются в облачной PostgreSQL, а пользователи могут пользоваться системой через браузер из интернета. На сервере реализованы проверки ролей и выдаётся только доступная пользователю информация. Такая инфраструктура важна, потому что комиссия видит не только код, но и реальный работающий продукт.

**Визуальные подсказки:**
- Схема “Browser → Frontend → Backend → PostgreSQL”
- Подпись: `VITE_API_URL` и `DATABASE_URL`
- Иконка Railway + иконка базы

**Технические якоря:**
- REST API: `/agents/*`, `/assistant/*`, `/progress/{user_id}`, `/recommendations/{user_id}`
- Профиль: таблица `cognitive_profiles` (JSON `payload`)

### Слайд 7. Данные ученика: когнитивный профиль и метрики

**Заголовок:** Уровень, точность и внутренние очки

**Текст для тела слайда:**
**Когнитивный профиль (что хранит):**
- `topic_mastery`: освоение тем (0…1)
- `task_history`: история попыток и правильность
- `error_frequency`: частота типов ошибок
- `accuracy_rate`: процент правильных попыток
- `points`: внутренние очки (геймификация)

**Зачем это нужно:**
- `topic_mastery` → выбираем слабые темы для адаптивных заданий
- `accuracy_rate` → оцениваем динамику и удерживаем мотивацию
- `error_frequency` → объясняем, какой именно тип ошибки повторяется и что повторять

**Спикер-скрипт:**
На этом слайде я объясняю, что именно делает систему адаптивной. Адаптивность в AdaptEd реализована через когнитивный профиль ученика. Он содержит численные показатели освоения тем, историю попыток и структуру ошибок. Именно поэтому мы можем не только посчитать точность, но и понять “тип проблемы”. Уровень и внутренние очки — это элемент мотивации и прогресса. Вся информация сохраняется в облачной базе PostgreSQL на Railway.

**Визуальные подсказки:**

**Технические якоря:**
- Профили — JSON в `payload` (таблицы `cognitive_profiles`)

### Слайд 8. Адаптивные задания, подсказки и эволюция ИИ

**Заголовок:** Как система подстраивается в момент решения

**Текст для тела слайда:**
**Адаптивные задания:**
- Система выбирает целевую тему из слабых: темы с низким освоением получают приоритет

**Подсказки (hint):**
- Режим подсказки предназначен, чтобы не раскрывать полный ответ
- Эндпоинт: `POST /assistant/hint`
- Принцип: короткая подсказка “по шагам”, наводящие вопросы, следующий шаг
- Retrieval контекста реализован как упрощённый поиск по содержимому документов (в дальнейшем планируется полноценный векторный поиск)

**Эволюция ИИ‑контура:**
- На этапе проверки гипотез использовалась Ollama‑сценария (для тестирования работы агентной схемы)
- Для production‑доступа и стабильности используется внешняя модель через API‑провайдер (NeuroAPI / GPT‑4o‑mini в интеграции)

**Спикер-скрипт:**
Здесь я показываю, где именно работает персонализация “в момент решения”. AdaptiveTask выбирает тему из слабых мест профиля. Затем LLM генерирует условие так, чтобы UI мог корректно показать вопрос и ожидаемый ответ. Если ученик просит подсказку, включается режим hint: подсказка направляет по шагам и не раскрывает решение целиком. И отдельно я поясняю важное: на ранних этапах мы проверяли идею и работу агентного контура с помощью Ollama. Для стабильной работы на публичном сайте используется production‑провайдер модели (NeuroAPI / GPT‑4o‑mini). Это обеспечивает предсказуемое поведение и доступность.

**Визуальные подсказки:**
- Мини‑пример JSON (в виде “облака” на слайде, без кода в детали)
- Иконки: “adaptive” + “hint”
- Стрелка: “слабая тема → задание”

**Технические якоря:**
