# Часть I. Большая картина

## Глава 1. Что вы вообще сделали (простыми словами)

Представьте **обычную школу**, но часть работы ведёт **компьютер**:

1. Ученик заходит на сайт.
2. Решает задачи, читает материалы, пишет в чат «помоги с дробями».
3. Система **запоминает**, где он ошибается, и даёт **другие** задания или материалы.
4. Учитель видит, у кого в классе провалы по темам.
5. Админ настраивает предметы, темы, пользователей.

**Ваша дипломная работа** — это не «просто сайт с задачками». Это система, где:

- есть **роли** (ученик / учитель / админ);
- есть **база данных** (всё сохраняется);
- есть **логика персонализации** (агенты + профиль ученика);
- есть **умный чат** (подключение к большой языковой модели через интернет).

Три слова, которые нужно запомнить:

| Слово | Простой смысл |
|-------|----------------|
| **Клиент** | Браузер с вашим интерфейсом (React) |
| **Сервер** | Программа на Python (FastAPI), которая принимает запросы и решает, что делать |
| **База данных** | Место, где лежат пользователи, тесты, оценки, профили |

Между клиентом и сервером они **разговаривают по HTTP** — это стандартный «язык» веба. Формат данных — обычно **JSON** (текст, похожий на словарь: `"имя": "Иван"`).

## Глава 2. Что происходит, когда вы открываете сайт

Разберём **один день ученика** без терминов «REST» и «Bearer» — их введём позже.

### Шаг 1. Открыли адрес

Вы вводите адрес сайта платформы (URL).  
Браузер загружает **фронтенд** — это готовые файлы React (HTML, JS, CSS), собранные Vite.

**Аналогия:** фронтенд — это **витрина магазина**: кнопки, формы, красивые экраны. Сама витрина не хранит все товары на складе — она **просит склад** (сервер) принести данные.

### Шаг 2. «Вы уже вошли?»

Приложение (`App.tsx`) спрашивает: есть ли в браузере сохранённый **пропуск** (токен)?

- **Нет** → показывается экран входа (`Auth.tsx`).
- **Да** → отправляется запрос на сервер: «проверь, жив ли мой пропуск?» (`GET /auth/me`).
  - Сервер отвечает «ок» → открывается кабинет ученика.
  - Сервер отвечает «просрочено» → снова экран входа.

### Шаг 3. Кабинет ученика

`StudentDashboard.tsx` показывает вкладки: обзор, задания, чат, библиотека, домашка.

Каждая вкладка **не считает всё сама в браузере** — она **запрашивает у сервера**, например:

- «дай мой прогресс» → `GET /progress/student_001`;
- «дай домашние работы» → `GET /homeworks?...`.

### Шаг 4. Решил задачу

Ученик вводит ответ → нажимает «Проверить» → фронт отправляет на сервер:

«Вот мой id, вот задача, вот мой ответ».

Сервер:

1. Сравнивает с правильным ответом.
2. Если ошибка — **классифицирует** тип ошибки (агент-анализатор).
3. **Обновляет профиль** ученика (агент-профилировщик).
4. **Генерирует** короткое сообщение поддержки (агент-наставник).
5. Отправляет всё обратно в JSON.

Фронт показывает: правильно/неправильно, подсказку, может обновить график прогресса.

**Главная мысль:** браузер **показывает**, сервер **думает и помнит**.

## Глава 3. Два приложения = два проекта в папке

В репозитории **два отдельных приложения**, которые работают в паре:

```
AdaptEd/
  frontend/   ← то, что видит пользователь (React)
  backend/    ← то, что обрабатывает логику (Python + FastAPI)
```

### Почему так делают почти везде

| | Frontend | Backend |
|---|----------|---------|
| Язык | TypeScript / JavaScript | Python |
| Где выполняется | В браузере пользователя | На сервере (Railway) |
| Можно ли спрятать секреты | **Нет** — весь код JS виден | **Да** — ключи API, пароли БД только тут |
| Задача | Удобный интерфейс | Безопасность, БД, ИИ, бизнес-правила |

**На защите говорите:** «Реализована классическая архитектура SPA + REST API: клиент на React, сервер на FastAPI».

### Как они связаны при разработке

На этапе разработки обычно два сервиса:

1. Backend: `uvicorn app:app --port 8000` → API по URL бэкенда (из конфигурации)
2. Frontend: `npm run dev` → сайт по URL dev-сервера

Фронт **всегда стучится** на порт 8000 за данными (если не собран для production с другим URL).

| Реальность | В проекте AdaptEd |
|------------|-------------------|
| Гость | Пользователь (ученик) |
| Зал, меню, официант | Frontend (React) |
| Кухня, повара, рецепты | Backend (FastAPI) |

| Заказ на бумажке | HTTP-запрос (JSON) |

Так и React **не проверяет математику глубоко** — он отправляет ответ на сервер, там работают агенты и правила.

# Часть II. Frontend — что видит пользователь

## Глава 5. React и «компоненты»

**React** — библиотека, где интерфейс разбит на **компоненты** (кусочки экрана).

Примеры из вашего проекта:

- `Auth` — форма входа;
- `StudentDashboard` — весь кабинет ученика;
- `AdaptiveTask` — экран одной адаптивной задачи;
- `AIChatPanel` — окно чата.

У каждого компонента есть **состояние** (`useState`): что сейчас на экране — загрузка, ошибка, список ДЗ и т.д.

**Пример логики** (упрощённо):

```
когда компонент StudentDashboard появился на экране
  → взять user_id из localStorage
  → запросить GET /progress/{user_id}
  → когда ответ пришёл → сохранить в state → нарисовать графики
```

Вы **не обязаны** помнить синтаксис React наизусть. На защите важно:

- интерфейс **модульный**;
- данные приходят **с сервера**;
- после логина **роль** определяет, какой дашборд показать (`App.tsx`).

### Файлы, которые стоит открыть один раз

| Файл | Зачем смотреть |
|------|----------------|
| `frontend/src/App.tsx` | Вход, роли, какой дашборд |
| `frontend/src/services/auth.ts` | Логин, сохранение токена |
| `frontend/src/services/api.ts` | Как все запросы получают токен |
| `frontend/src/components/StudentDashboard.tsx` | Жизнь ученика в UI |

## Глава 6. Как фронт «звонит» на сервер (axios)

**axios** — библиотека для HTTP-запросов из JavaScript.

В `api.ts` создаётся один общий объект `api` с базовым адресом:

- режим разработки: URL бэкенда из `VITE_API_URL`;
- production: адрес из `VITE_API_URL` (Railway).

### Interceptor — «перехватчик»

Перед **каждым** запросом axios автоматически:

1. Читает `token` из `localStorage`.
2. Добавляет заголовок: `Authorization: Bearer <token>`.

Вам не нужно вручную писать это в каждом компоненте — один раз настроено в `api.ts`.

Если сервер ответил **401** (не авторизован) — перехватчик **очищает** токен и кидает на страницу входа.

**Проверьте понимание:**  
*Почему токен в localStorage, а не в коде?*  
→ Потому что после перезагрузки страницы пользователь должен остаться залогиненным, пока токен действует.

## Глава 7. Три роли — три разных экрана

После входа `App.tsx` смотрит поле `role` пользователя:

| role | Компонент |
|------|-----------|
| `student` | `StudentDashboard` |
| `teacher` | `TeacherDashboard` |
| `admin` | `AdminPanel` |

Админ дополнительно может **переключать вид** (как будто он ученик) — для демонстрации на защите.

**Безопасность:** переключение вида в UI **не даёт** прав ученика на сервере, если API проверяет роль из **токена**, а не из того, что прислал фронт. В вашем проекте проверки на бэкенде есть (`require_roles`, `assert_can_view_user_data`).

# Часть III. Backend, данные и «язык» веба

## Глава 8. FastAPI — сердце сервера

**FastAPI** — фреймворк на Python. Вы описываете:

```python
@router.post("/auth/login")
async def login(login_data: UserLogin):
    ...
```

Это значит: «если пришёл **POST** на путь `/auth/login` с телом JSON — выполни функцию `login`».

### Что FastAPI делает за вас

1. **Принимает** HTTP-запрос.
2. **Парсит** JSON в объект Pydantic (`UserLogin` — поля `email`, `password`).
3. **Вызывает** вашу логику (`auth_service.authenticate_user`).
4. **Возвращает** JSON и код статуса (200, 401, …).
5. **Рисует** документацию на `/docs` — удобно показать комиссии.

Точка сборки всех роутов — `backend/app.py`: там `include_router` для auth, agents, homework и т.д.

### Uvicorn

**Uvicorn** — программа, которая **запускает** FastAPI и слушает порт 8000.  
Без него файл `app.py` — просто код; с uvicorn — работающий сервер.

## Глава 9. JSON и HTTP — «как они разговаривают»

### HTTP-метод = глагол действия

| Метод | Обычный смысл | Пример в AdaptEd |
|-------|---------------|------------------|
| **GET** | Прочитать, получить | `GET /auth/me` — кто я |
| **POST** | Отправить данные, создать, действие | `POST /auth/login` — войти |
| **PUT** | Обновить целиком | `PUT /auth/profile` |
| **DELETE** | Удалить | `DELETE /tests/5` |

### Код ответа = результат операции

| Код | Значение | Когда у вас |
|-----|----------|-------------|
| **200** | Успех | Данные отданы |
| **201** | Создано | Регистрация, новый тест |
| **401** | Не авторизован | Нет токена / неверный пароль |
| **403** | Запрещено | Ученик лезет в админку |
| **404** | Не найдено | Нет такого теста |
| **500** | Ошибка сервера | Падение БД, баг |

### JSON — пример

Запрос входа:

```json
{
  "email": "student_001@school.ru",
  "password": "secret123"
}
```

Ответ при успехе:

```json
{
  "access_token": "длинная_строка...",
  "token_type": "bearer",
  "user_id": "student_001",
  "role": "student",
  "full_name": "Иван Иванов"
}
```

**REST API** — это когда такие запросы **единообразны**: разные ресурсы — разные URL, одни и те же методы, данные в JSON. Ваш backend — **REST API**.

## Глава 10. База данных — где «память» системы

### Зачем БД, если есть файлы

Файл `data.json` подходит для прототипа. В школе одновременно:

- много учеников,
- тесты, попытки, домашки,
- нужны **надёжность** и **поиск** (все ученики 5А).

Для этого — **реляционная БД** (PostgreSQL): таблицы со связями.

### Таблица — как Excel-лист

**users** — одна строка = один пользователь:

| user_id | email | password_hash | role | full_name |
|---------|-------|---------------|------|-----------|
| student_001 | ... | a3f9... | student | Иван |

**tests** — один тест; **test_questions** — вопросы; **test_submissions** — кто что сдал.

### SQLAlchemy (ORM)

Вы пишете на Python:

```python
user = db.query(UserDB).filter(UserDB.email == email).first()
```

SQLAlchemy **переводит** это в SQL.  
Не обязательно писать `SELECT * FROM users WHERE ...` руками.

### Профили в JSON внутри БД

Когнитивный профиль **большой и гибкий** (много полей, история). Его хранят в таблице `cognitive_profiles`:

- колонка `user_id`;
- колонка `payload` — весь профиль одним JSON.

Так проще менять структуру профиля без десятка новых колонок.

### Иерархия учебного контента

```
Предмет (Математика)
  └── Раздел (Алгебра)
        └── Тема (Дроби)
              └── Задания, ссылки на материалы библиотеки
```

Таблицы: `curriculum_subjects`, `curriculum_sections`, `curriculum_topics`.

**На защите:** «Контент структурирован иерархически; это основа библиотеки, тестов и рекомендаций».

# Часть IV. Вход в систему (подробно, без магии)

## Глава 11. Пароль — почему не хранится «как есть»

При регистрации пароль `"secret123"` **не кладут** в БД.

1. Сервер считает **хеш** (у вас SHA-256) — одностороннее преобразование.
2. В БД пишут `password_hash`.

При входе:

1. Хешируют введённый пароль тем же способом.
2. Сравнивают с тем, что в БД.

Даже если кто-то украдёт БД, **восстановить пароли сложно** (для диплома честно скажите: в промышленности берут bcrypt/argon2 — у вас упрощение прототипа).

## Глава 12. Bearer-токен — «пропуск на руки»

После успешного логина сервер выдаёт **токен** — длинную строку.

### Из чего он состоит (ваш проект)

1. **Payload** (содержимое), например:
   - `user_id`: кто вы;
   - `role`: student / teacher / admin;
   - `exp`: до какого времени действует.
2. **Подпись** — чтобы нельзя было подделать payload без секретного ключа `AUTH_SECRET_KEY`.

Формат: `payload_base64.signature_base64`

### Как им пользуются

Каждый запрос после входа:

```http
GET /homeworks
Authorization: Bearer eyJ1c2VyX2lkIjoi...
```

Сервер:

1. Отрезает слово `Bearer `.
2. Проверяет подпись.
3. Проверяет, не истёк ли срок `exp`.
4. Достаёт `user_id` и `role` — **доверяет им**, если подпись верна.

**Stateless** значит: серверу **не обязательно** хранить список «кто сейчас онлайн» в оперативной памяти. Вся информация для проверки — в самом токене + секрет.

### Полный цикл (повторите вслух)

1. `POST /auth/login` + email + password.  
2. Сервер проверяет БД → строит токен.  
3. Ответ: `access_token`, `user_id`, `role`.  
4. Фронт: `localStorage.setItem('token', ...)`.  
5. Любой следующий запрос: заголовок `Authorization: Bearer ...`.  
6. `GET /auth/me` — «кто я?» для восстановления сессии после F5.  
7. `logout` — удалить token из localStorage.

**На защите:** «Разграничение доступа реализовано на сервере, не только скрытием кнопок в интерфейсе».

# Часть V. «Мозг» персонализации

## Глава 14. Зачем агенты, если есть один Python-файл

Можно было написать одну функцию на 2000 строк: проверить ответ, обновить статистику, написать текст, сгенерировать задачу…

Вы разделили на **агентов** — модули с **одной ответственностью**:

| Агент | Одна фраза о роли |
|-------|-------------------|
| **ErrorAnalyzer** | «Почему ошибся?» — тип ошибки |
| **Profiler** | «Что мы знаем об ученике?» — профиль |
| **Mentor** | «Что сказать человеку?» — поддержка |
| **TaskGenerator** | «Что дать решить дальше?» — задачи из банка |
| **TeacherAnalytics** | «Что показать учителю?» — сводки по классу |
| **AdaptiveEducator** | «Что выяснилось из чата и тестов?» — расширенная аналитика |

**Оркестратор** (`AgentOrchestrator`) — дирижёр: вызывает агентов **в нужном порядке** и собирает ответ.

### Сценарий: ученик отправил ответ (пошагово)

```
1. Фронт: POST /agents/submit-task
   { user_id, task_id, question, user_answer, correct_answer, topic }

2. Оркестратор:
   а) Правильно ли? (строка или числа с допуском 0.001)
   б) Если нет → ErrorAnalyzer → error_type, совет
   в) Profiler → обновить CognitiveProfile (история, accuracy, темы)
   г) Mentor → message для UI
   д) Вернуть JSON фронту

3. Фронт показывает результат и сообщение наставника
```

Нарисуйте на защите **4 блока слева направо** — комиссия любит схемы.

### Типы ошибок — зачем они

Не просто «неправильно», а **категория**:

- путаница в понятии;
- арифметика;
- невнимательность;
- не применил формулу.

Из этого потом:

- статистика в профиле;
- выбор следующих задач;
- рекомендации материалов по слабой теме.

## Глава 15. Когнитивный профиль — «досье ученика»

Это **не** таблица users. Это отдельная структура `CognitiveProfile`:

| Поле | Простой смысл |
|------|----------------|
| `topic_mastery` | Насколько освоена тема (0…1) |
| `task_history` | Какие задачи решал |
| `error_frequency` | Какие типы ошибок чаще |
| `accuracy_rate` | % правильных |
| `points`, `level` | Мотивация, геймификация |
| `material_study_history` | Что читал из библиотеки |
| `current_emotional_state` | Для тона сообщений наставника |

Обновляет в основном **ProfilerAgent** после каждой попытки.

### Батчинг — зачем не писать в БД каждую секунду

Если ученик быстро решает 10 задач — 10 записей в БД подряд **медленно**.

**BatchedSaver** копит изменения и сохраняет **пачкой** раз в несколько секунд или при остановке сервера.

**Аналогия:** не выносить мусор после каждого яблока, а когда мешок полный.

## Глава 16. AI-чат — отдельный контур

Это **не то же самое**, что агенты-правила. Здесь подключается **большая языковая модель** (LLM) через интернет.

### Цепочка

```
Ученик пишет в чат
  → POST /assistant/chat
  → AssistantService
  → HTTP-запрос к ProxyAPI (OpenAI-совместимый API) с промптом
  → Модель генерирует текст
  → Ответ сохраняется в chat_sessions
  → Фронт показывает сообщение
```

### Провайдеры (переменные окружения)

- **proxyapi** + `PROXYAPI_KEY` — основной вариант (GPT-4o и др.);
- **hf_api** — Hugging Face;
- **local** — модель на сервере (тяжело, редко на дипломе).

Без ключа пользователь видит вежливое «ассистент временно недоступен» — не падение всего сайта.

### PersonalityProfile

Система может учитывать **стиль общения** ученика (черты, тон) и подстраивать промпт — данные в БД, не «магия модели».

### Честно для комиссии

- **Агенты** — в основном правила и эвристики на вашем сервере.  
- **LLM** — генерация **текста** (объяснения, диалог).  
- **RAG** (поиск по учебникам + ответ) в полном виде — **план развития**; сейчас рекомендации материалов — по темам и слабым местам из профиля.

# Часть VII. Деплой — как это оказывается в интернете

## Глава 17. Размещение на Railway

**Railway:** два **сервиса** в облаке:

1. Backend — `DATABASE_URL`, `AUTH_SECRET_KEY`, `PROXYAPI_KEY`.
2. Frontend — при **сборке** нужен `VITE_API_URL` = публичный URL бэкенда.

Если забыть `VITE_API_URL`, фронт в production будет стучаться «не туда» — типичная ошибка, вы её уже описали в `START_HERE.md`.

**CORS** — разрешение браузеру с домена фронта обращаться к домену API. Настроено в `app.py`.

## Глава 19. Шпаргалка устных ответов (простым языком)

**Что за система?**  
Веб-платформа для школьников: задания, тесты, библиотека, чат с ИИ; подстраивается под ошибки и прогресс ученика.

**Из чего состоит?**  
Сайт на React, сервер на Python FastAPI, база PostgreSQL, внешняя языковая модель для чата.

**Как клиент и сервер общаются?**  
REST API: запросы HTTP, данные JSON; после входа — Bearer-токен в заголовке.

**Что такое адаптивность?**  
После каждого ответа обновляется профиль ученика, учитываются типы ошибок и темы — от этого зависят следующие задачи и рекомендации.

**Что такое агенты?**  
Отдельные модули с одной задачей; оркестратор вызывает их по цепочке при проверке ответа.

**Чем LLM отличается от агентов?**  
Агенты — правила на сервере; LLM — нейросеть в облаке для свободного текста в чате.

**Слабые места прототипа?**  
SHA-256 для паролей; нет полного RAG; миграции через create_all; токен нельзя отозвать до истечения срока.
